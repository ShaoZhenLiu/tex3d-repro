## 一、四大结论（全部有日志可溯源）

1. **攻击层面四模型全部复现有效**（统一"任务失败率"口径）：π0 83.0/70.0/77.8/93.0（spatial/object/goal/long@520），OpenVLA 72.0/84.0，OFT 96.2/54.2；相对各自 clean 提升 +27~+87pp；迁移 OpenVLA→π0 84.4%、π0→OpenVLA 27.4%。
2. **clean 基线之谜已定性为上游问题**：用官方 RLinf 栈（openpi `serve_policy.py`+`examples/libero/main.py` 原样）+ 官方发布权重复测，clean 失败率 37.6/33.0/47.0/66.2，与我们自建栈（38.4/29.4/41.2/66.0）完全一致（Δ≤5.8pp），与论文（3.5/2.3/5.2/7.2）差 30-60pp → 嫌疑只剩：HF 权重版本 ≠ 作者实际版本 / 作者环境 / 论文口径未披露。
3. **发现上游三个可验证缺陷**（issue 素材，草稿已写好）：
   - ① 指标标签反转：`attack_openvla.py:1344`、`attack_oft.py:1576` 打印的 "Attack success rate" 实为受攻击下机器人任务成功率（真实攻击成功率=100%−打印值）；大概率解释社区"OFT 95% vs 0%"之争（我们 v1 报告也曾误读，已全面更正）；
   - ② π0 烘焙不等价：训练逐像素采样原纹理、导出却顶点采样后插值，零扰动也不恢复原纹理（实测 PSNR：wine 标 3.2dB、akita 25.1dB、moka 20.8dB、cream 16.8dB）；白盒数字不受影响，影响部署/视频；修复方案（只烘噪声场）已验证零误差；
   - ③ 发布权重 clean 与论文不符（见结论 2 的表）。
4. **改进实验（种子 A）诚实结论**：TAAO 移植对 OpenVLA 增益任务依赖且有限（t1 80→92、t0 52→58、t7 38→36、t2 饱和），逐像素底图(px)无叠加增益（t0 58→60、t1 持平 92），弱任务是纹理攻击内在盲区（负结果但干净）；分辨率 256/224 经单变量实验排除（t0 四变体 84-92%，噪声内）。

## 四、服务器现状与运维要点

- **我们的任务已全部停止**（用户要求保稳定），各卡仅 ~850MB 底噪；GPU0 有他人 5.4GB；
- **10-11 凌晨曾发生驱动级联故障**（GPU1 崩→全机 CUDA 999），重启后恢复；若再遇 "CUDA unknown error" 全卡齐报 → 找管理员重启，勿浪费时间排查自己进程；
- 跑任务模板：`cd <ws> && env CUDA_VISIBLE_DEVICES=N MUJOCO_EGL_DEVICE_ID=N MUJOCO_GL=egl PYOPENGL_PLATFORM=egl HF_HUB_OFFLINE=1 PYTHONPATH=/data/shaozhen.liu/code/tex3d:/data/shaozhen.liu/code/tex3d/openvla <venv>/bin/python <脚本> ...`；
- 工作区：`tex3d-ws/{g5,ov2,ov6,...}` 各含 OpenVLA ckpt；编排 `tex3d-deps/{runner.sh,jobs_*.txt,chains/}`；
- **血泪教训**：pkill/pgrep 模式必须括号防自匹配（`pkill -f "xxx_[t]ag"`），且 kill 与启动不可同条命令；π0 脚本无 `--run_id_note` 参数（OpenVLA 脚本有）；官方 websocket 栈首推理 371s 惰性编译会踢爆 20s keepalive，需先跑 `rlinf_eval/warmup_probe2.py <port>` 预热；tyro 参数顺序敏感（`--port` 须在 `policy:checkpoint` 前）。
